# Doc PR — 4차 정상화 지시서 (컨테이너 감축 · 마이페이지 · 뒤로가기)

> `normalization_v3.md` 이후 작업. 기능·데이터 구조는 유지한다. 이번 라운드는
> **(1) 여전히 난잡한 원인을 다시 진단해 시각적으로 정리하는 작업**과
> **(2) 빠져 있던 화면·내비게이션 두 가지를 새로 만드는 작업**을 함께 한다.

---

## 0. 사용자 피드백

> "컨테이너(요소 박스)가 너무 많아서 기능이 한눈에 들어오지 않고 난잡하다."
> "마이페이지가 구현이 안 됐다."
> "뒤로가기 버튼이 없다."

3차가 카드를 64장 → 44장으로 줄였는데도 여전히 난잡하다고 느껴진다면, **문제는
`Card` 컴포넌트 개수가 아니라 화면에 보이는 "테두리 쳐진 사각형"의 총량**일 가능성이
높다. 3차 계측은 `Card` 컴포넌트만 셌고, 버튼·입력창·배지·표 셀·필터 바·아코디언
머리·사이드바 항목처럼 **`Card`가 아니면서도 테두리·배경·그림자로 자기 영역을 주장하는
요소**는 세지 않았다. 1장에서 이 부분을 먼저 다시 진단한다.

---

## 1. 재진단 — "컨테이너"의 정의를 넓힌다

지금까지 세 차례 정상화는 전부 `Card` 컴포넌트 사용 여부만 판단 기준으로 삼았다.
이번엔 판단 대상을 넓힌다. 아래 중 하나라도 해당하면 "컨테이너"로 센다.

- 테두리(`border`)가 있는 모든 요소 — 카드뿐 아니라 버튼, 입력창, 배지, 필터 바, 탭,
  아코디언 헤더, 툴팁, 표의 셀/행.
- 배경색이 투명이 아니면서 모서리가 둥근(`rounded-*` + 배경) 모든 요소.
- `box-shadow`가 있는 모든 요소.

### 1.1 새 계측 방법
화면마다 위 조건에 해당하는 DOM 요소 수를 (Playwright 등으로) 세어 **"컨테이너
총계"**를 낸다. `Card` 개수만 세던 3차의 표는 이 총계로 교체한다. 화면당 목표치는
정하지 않는다 — 대신 2장의 요소별 규칙을 적용한 뒤 자연히 줄어든 값을 "이후" 값으로
기록한다(3차와 같은 before/after 표 형식 유지).

### 1.2 왜 지금까지 안 잡혔나
- 배지(Badge/Chip)가 목록·표 안에서도 전부 알약(pill) 채움 스타일이었다면, 상태
  하나당 컨테이너 하나가 추가된 것과 같다. 표 한 화면에 행이 7개면 배지만으로
  컨테이너 7개가 생긴다.
- outline 버튼도 "박스 없앤 것"으로 3차에 카운트되지 않았지만, 테두리가 있는 사각형인
  건 마찬가지다.
- 입력창은 3차 논의에서 아예 다뤄지지 않았다 — 상자형 테두리 입력창이 화면마다
  여러 개면 그 자체로 컨테이너 벽을 만든다.
- 표(`DataTable`)의 셀/행 구분선이 격자무늬로 촘촘하면, Card를 표로 바꾼 게 오히려
  더 조밀한 박스 감각을 줄 수 있다(3차가 `documents`·`team-members`에서 Card를
  DataTable로 옮긴 지점을 재점검 대상에 넣는다).

## 2. 요소별 규칙 (구조적 테두리만 남기고 나머지는 제거)

"구조적"이란 **그 테두리가 없으면 사용자가 조작 가능한 영역의 경계를 알 수 없는
경우**만 말한다. 그 외엔 여백과 색만으로 구분한다.

| 요소 | 지금까지 | 이번 규칙 |
| --- | --- | --- |
| 주 버튼(화면당 1개) | 배경 채움 | 유지 (구조적 — 유일한 강조) |
| 나머지 버튼 | outline(테두리) | **테두리 제거** — 텍스트/아이콘 + hover 시에만 옅은 배경 |
| 입력창(폼) | 사방 테두리 박스 | **밑줄(하단 테두리)만** — 포커스 시에만 전체 테두리 |
| 배지(목록·표 안) | 알약 채움 | **점(dot) + 텍스트**로. 알약 채움은 상세 화면 헤더처럼 배지가 유일하게 강조되는 자리에만 |
| 배지(단독 강조 자리) | 알약 채움 | 유지 (구조적 — 상태를 즉시 인지해야 하는 자리) |
| 표(DataTable) | 셀/행 격자선 | **가로 구분선만**(행 사이), 세로선 없음, 헤더 밑줄 1개 |
| 필터/검색 바 | 상자 안에 인풋 나열 | 상자 제거, 인풋 자체의 밑줄 스타일만으로 나열 |
| 아코디언(`Disclosure`) 헤더 | 테두리/배경 있는 경우 있음 | 텍스트 + 화살표만, 배경·테두리 없음 |
| 사이드바 항목 | 선택 시 배경 박스 | 유지하되 더 옅게(3차가 이미 `neutral-75`로 낮춤 — 유지) |
| 탭(Tabs) | 각 탭이 박스인 경우 | 밑줄 인디케이터 방식으로(선택 탭 아래 2px 브랜드색 선) |
| 툴팁/드롭다운 | 필요시 유지 | 유지 (구조적 — 뜨는 순간만 존재하는 임시 표면) |

이 표를 적용하면 "카드 개수"는 이미 낮아진 3차 수준을 유지하면서, **화면에 보이는
테두리/배경 총량 자체가 눈에 띄게 줄어든다.** 이게 "기능이 한눈에 들어온다"는 감각의
실제 원인이다 — 사용자는 Card 컴포넌트를 세지 않는다, 눈에 보이는 선을 센다.

## 3. 신규 — 마이페이지

`화면-목록.md`의 20개 화면 어디에도 개인 계정 화면이 없다. 그런데 API 명세서에는
`PATCH /users/me`(개인 프로필 설정 — 이름·시간대·선호 언어 수정, 이미 "완료"로
표시된 API)가 있다. **화면이 빠진 채 API만 정의돼 있던 상태**다. 이번에 새로 만든다.

### 3.1 범위
기능명세서·API 명세서에 실제로 근거가 있는 항목만 넣는다(이 지시서 시리즈의 "없는
기능을 새로 만들지 않는다" 원칙은 마이페이지에도 동일 적용):
- 기본 정보 — 이름, 이메일(읽기 전용), 시간대, 선호 언어(`PATCH /users/me` 대응)
- 소속 팀 목록 — 현재 속한 팀과 그 팀에서의 RACI 역할(1·2차가 만든 `raci.js`,
  `MyRoleBar`의 데이터를 재사용)
- 로그아웃(`POST /auth/logout` 대응, 실제 호출은 하지 않고 로그인 화면으로 이동만)
- 그 외(알림 수신 설정, 비밀번호 변경 등) API/기능명세서에 근거가 없으면 넣지 않고
  "후속 단계 범위"로도 언급하지 않는다 — 아예 화면에 없는 게 맞다.

### 3.2 진입점
상단바 우측에 사용자 아바타/이름이 진입점 역할을 해야 한다. 현재 상단바 구성을
먼저 점검하고, 진입점이 없다면 이번에 추가한다(상단바는 3차에서 검색창만 남기고
정리된 상태 — 우측 아바타 자리를 새로 마련).

### 3.3 라우트
`#/me`로 등록하고 `화면-목록.md`에 21번째 화면으로 추가한다.

### 3.4 스타일
과거처럼 먼저 만들고 나중에 다시 정리하는 낭비를 없애기 위해, **2장의 컨테이너
규칙을 처음부터 적용해서 만든다.** 입력창은 밑줄 스타일, 소속 팀 목록은 표 형태
구분선만, 저장 버튼 하나만 강조.

## 4. 신규 — 뒤로가기

지금은 사이드바로 최상위 섹션 이동만 가능하고, **상세/하위 화면에서 상위 화면으로
돌아가는 명시적인 경로가 없다.** 브라우저 뒤로가기에만 의존하는 것은 해시 라우팅
특성상 항상 예측 가능하지 않으므로, 화면 안에 뒤로가기를 명시적으로 둔다.

### 4.1 구현 방식
`PageHeader`(1차가 만든 화면 골격 컴포넌트)에 `backTo` prop을 추가한다. 값이 있으면
제목 위/좌측에 "← [상위 화면 이름]" 텍스트 링크가 뜬다. 아이콘 하나 + 텍스트,
테두리 없음(2장 규칙과 동일하게 장식 없는 링크 스타일).

### 4.2 상위-하위 매핑 (`유저플로우.md` 기준)
| 하위 화면 | `backTo` |
| --- | --- |
| Doc PR 상세 | Doc PR 목록 |
| AI 리뷰 결과 | Doc PR 상세 |
| 사람 리뷰 | Doc PR 상세 |
| 승인권자 지정 | Doc PR 상세 |
| 문서 작성/편집 | 문서 목록 (신규 작성 진입이 대시보드였다면 대시보드) |
| AI 구조 추천(딥링크) · 관련 문서 연결 · 번역 보기 | 문서 작성/편집 |
| RACI 역할 관리 · 협업 규칙(Charter) · 팀 용어집 관리 · 팀원 관리 | 팀 설정/관리 |
| 팀 설정 초기화 | 팀 생성/참여 (기존 화면-목록.md 2차 메모에 이미 있는 링크 방향과 일치) |
| 마이페이지(`#/me`) | 직전 화면(고정된 상위가 없는 진입점이므로 브라우저 컨텍스트 유지 — 뒤로가기 링크는 "닫기"로 표기) |

최상위 화면(대시보드, 문서 목록, Doc PR 목록, Document Graph, 팀 설정/관리)은
`backTo`가 없다 — 사이드바가 곧 이동 수단이므로 뒤로가기를 억지로 만들지 않는다.

## 5. 작업 순서 제안

1. **`PageHeader`에 `backTo` 추가** — 매핑표(4.2) 순서대로 12개 화면에 적용. 가장
   빠르게 "탐색 가능한 서비스"라는 인상을 준다.
2. **마이페이지 신설** — 3장 그대로. 진입점(상단바)까지 함께 만들어야 실제로 접근
   가능하다.
3. **요소별 컨테이너 규칙 적용(2장)** — 버튼 → 입력창 → 배지 → 표 → 필터 바 →
   아코디언 → 탭 순으로, 전 화면에 동일 규칙을 일괄 적용한다(컴포넌트 단위 수정이라
   화면 하나씩이 아니라 컴포넌트 하나 고치면 여러 화면에 한 번에 반영된다는 점을
   활용 — `Button`/`Input`/`Badge`/`DataTable`/`Disclosure`/`Tabs` 공용 컴포넌트를
   먼저 고치고 화면은 그 결과를 확인만 한다).
4. **컨테이너 총계 재계측(1.1)** — 20개(+마이페이지 포함 21개) 화면 전수.

---

## 6. 완료 기준 (Definition of Done)

- [ ] 21개(기존 20 + 마이페이지) 화면 전수에서 "컨테이너 총계"(1장 정의)를 측정해
      3차의 `Card` 전용 수치보다 넓은 기준으로 before/after를 기록했다.
- [ ] 화면당 배경 채움 버튼은 여전히 최대 1개, 나머지 버튼은 테두리가 없다.
- [ ] 폼 입력창이 사방 테두리 박스가 아니라 밑줄 스타일이다(포커스 시 예외).
- [ ] 목록/표 안의 배지가 알약 채움이 아니라 점(dot)+텍스트다. 상세 화면 헤더처럼
      단독 강조가 필요한 자리의 배지는 알약 채움을 유지했다.
- [ ] `DataTable`이 세로 격자선 없이 가로 구분선만 사용한다.
- [ ] 마이페이지(`#/me`)가 존재하고, 이름/시간대/선호 언어를 표시·수정할 수 있으며
      (API 연동은 하지 않음), 소속 팀과 RACI 역할이 보이고, 로그아웃 진입점이 있다.
- [ ] 상단바에 마이페이지로 가는 진입점(아바타/이름)이 있다.
- [ ] 4.2 매핑표의 12개 하위 화면 전부에 뒤로가기 링크가 있고, 실제로 클릭 시 지정된
      상위 화면으로 이동한다.
- [ ] `화면-목록.md`에 마이페이지(21번째 화면)와 뒤로가기 매핑이 반영됐다.
- [ ] 브랜드 컬러 값은 이번에도 바뀌지 않았다 — 이번 라운드도 "얼마나 많은 요소가
      테두리/배경을 쓰는가"를 줄이는 작업이지 색 자체를 바꾸는 작업이 아니다.
- [ ] API 호출 코드가 추가되지 않았다(마이페이지 포함, mock 데이터만 사용).
- [ ] 21개 라우트 전수 스윕 — 콘솔 에러 0건, 가로 오버플로 0건.
